# Level 3 block-quotient solver (`level3-block-quotient`)

Implementation: [`packages/solver-core/src/algorithms/level3BlockQuotientSolver.ts`](../../packages/solver-core/src/algorithms/level3BlockQuotientSolver.ts). Registered under algorithm id `level3-block-quotient` (see [`register.ts`](../../packages/solver-core/src/algorithms/register.ts)).

Like every solver in this repo it reads only the current `Cubie[]` state (never `moveHistory`), outputs replayable legal moves, and fails honestly with a structured explanation when the state is outside its scope.

## The key idea: the quotient of Level 3 is Level 2, exactly

The [Level 2 block quotient](level2-block-quotient-solver.md) works because a Level 2 state whose 3×3×3 blocks all move rigidly *is* a Level 1 state. The same step up from Level 3 does **not** land on Level 2-as-a-toy: it lands on Level 2 itself, in full.

Level 3 is a 27×27×27 sponge of 8000 cells. Group the grid into 3×3×3 **mid-blocks**; the Menger rule leaves 400 of them, and those 400 blocks are arranged in exactly the Level 2 cell pattern. Each mid-block holds exactly the 20 cells of a Level 1 shape. So "every mid-block is rigid" quotients Level 3 onto a 400-cell Level 2 puzzle — and the correspondence extends to the moves:

| Level 3 move | Macro Level 2 move |
| --- | --- |
| Scale-3 frame turn (27 targets) | Scale-1 slice |
| Scale-9 frame turn (9) | Scale-3 block layer |
| Depth-1 block extension `E1:*` (12) | Depth-1 block extension — **identical target id** |
| Depth-1.5 slab twist `S1.*` (36) | Depth-1.5 slab twist — **identical target id** |
| Depth-2 mid-block rotation `E2:*` (240) | Depth-2 cell roll — **identical target id** |
| Depth-3 cell roll `E3:*` (4800) | *invisible in the quotient* |

The extension target ids coincide because the generator addresses targets by recursive path (`extension:d<depth>:p<path>:s<slot>`), which is level-independent at the top scales. All 288 Level 2 extension ids exist verbatim at Level 3.

This is checked, not assumed. [`research/scratch/l3-structure.ts`](../../research/scratch/l3-structure.ts) verifies for every one of the 36 macro frames and 288 macro extension targets that

> the lifted Level 3 target selects cell `p` **iff** the macro target selects `midBlock(p)`

over all 8000 cells — 0 mismatches. The quotient map is exact, not approximate.

So the solver does not reimplement anything: it projects, calls the already-verified [Level 2 slice-reduction solver](level2-slice-reduction-solver.md), and lifts the answer back.

## Supported state class

The solver exactly solves every state generated by the **block-rigid generator set** — every legal move that keeps mid-blocks intact:

| Generator | Candidate targets | Physically legal | Effect |
| --- | --- | --- | --- |
| Scale-3 frame turns | 27 | 27 | Permute mid-blocks like a Level 2 slice |
| Scale-9 frame turns | 9 | 9 | Permute 9×9×9 sub-blocks |
| Depth-1 block extensions (`E1:*`) | 12 | 12 | Rotate one 9×9×9 edge block in place |
| Depth-1.5 slab twists (`S1.*`) | 36 | 36 | Rotate one 9×9×3 slab |
| Depth-2 mid-block rotations (`E2:*`) | 240 | 72 | Rotate one 3×3×3 mid-block in place |
| Depth-3 cell rolls (`E3:*`) | 4800 | 744 | Roll one unit cell in place |

That is 5124 of the puzzle's 5925 turn targets. The two excluded families — **scale-1 slices** (81) and **depth-2.5 slab twists** (720) — cut through mid-blocks, so a state that used them no longer projects onto Level 2. Phase 1 detects that and reports which region is torn and why. Repairing them needs a cell-level reduction: the Level 3 analogue of the [slice-reduction solver](level2-slice-reduction-solver.md), and the natural next rung of the tower (see [Future work](#future-work)).

Note the gap between *candidate* and *legal* targets: target generation and physical admissibility are separate concepts (see the [rotation legality design log](../architecture/rotation-legality-design-log.md)). Only 744 of 4800 depth-3 rolls can actually turn, which matters below.

## Algorithm

Algorithm name: `level-3-block-quotient-reducer`. Four phases.

### Phase 1: mid-block rigidity analysis

Partition the 8000 cells by which 3×3×3 region their `currentPosition` falls in. For each of the 400 regions, verify:

1. **Purity** — all 20 cells in the region come from the same home mid-block.
2. **Rigidity** — one of the 24 orientation-preserving cube rotations (exact integer matrices, shared via [`blockRotations.ts`](../../packages/solver-core/src/algorithms/blockRotations.ts)) maps every cell's home offset onto its current offset within the region.

Cell *orientations* are deliberately ignored here: a depth-3 roll turns a cell in place without moving it, so it cannot break rigidity — those are cleaned up in phase 4.

Each rigid region becomes one **macro cubie**, built from the canonical Level 2 cell of the same home coordinate (so ids and types match a real Level 2 state exactly), with `currentPosition` = region coordinate and `orientation` = the quaternion of the recovered rotation. Any failure stops the solve with a structured explanation naming the region and the obstruction.

### Phase 2: macro Level 2 solve

The 400 macro cubies are placed into a synthetic Level 2 `MengerPuzzleState` and handed to the registered `level2-slice-reduction` algorithm unchanged. That solver in turn fast-paths to `level2-block-quotient` when the macro state happens to be block-rigid, so the tower is three deep on that path: Level 3 → Level 2 → Level 1.

Because scale-3 frames at Level 3 map to scale-1 *slices* in the quotient, a generic scramble produces a macro state that is **not** block-rigid — which is exactly why the macro solver has to be the full slice-reduction solver rather than the block-quotient one.

### Phase 3: lift and verify

Each macro move lifts one fractal step:

- **frames** — a macro frame of scale `s` at layer `ℓ` becomes the Level 3 frame of scale `3s` at layer `3ℓ`;
- **extensions** — the same target id names the Level 3 target directly.

Lifted moves must also be *physically* legal, which is a separate question from being well-defined. It holds, and for a structural reason: the moving body of a lifted turn is a subset of the scaled macro body, and so is every stationary obstacle, so a collision at Level 3 implies a collision in the macro puzzle. `l3-structure.ts` confirms it exhaustively — all 468 macro-legal turns lift to legal Level 3 turns, 0 violations.

The lifted moves are then replayed on the real 8000-cell state with the real engine move functions, and every cell must be at its exact home position afterwards. This is verified, not assumed.

### Phase 4: cell roll normalization

Positions are now all home; only orientations can be wrong. Two facts make this phase a lookup rather than a search.

**Rolls compose in the cell's own frame.** Every move coarser than depth-3 turns a cell together with its whole mid-block, carrying the cell and its block frame as one, so the cell-relative orientation does not change — only a depth-3 turn changes it, and always about the cell's home slot axis. Writing a cell's orientation as `q = R·s` with `R` the block's rotation, a block move sends `R ↦ gR` and leaves `s` fixed, while a roll at the cell's current site sends `s ↦ R_a(θ)·s` for the *home* slot axis `a`. The macro solve ends with `R = I` for every block, so every residue is a pure roll about a known axis.

**Roll-legality is an orbit invariant.** With only 744 of 4800 depth-3 targets able to turn, a cell could in principle be rolled at one site and need unrolling at a blocked one. It cannot. Under the **full** move group — slices and depth-2.5 slabs included — the 8000 sites fall into 164 orbits, and roll-legality is constant on every one of them (`l3-structure.ts`: 0 mixed orbits). A cell that can be rolled anywhere can be rolled at home.

So for each twisted cell the solver takes the depth-3 target at its home site and applies the one angle of `+90 / -90 / 180` that restores the identity orientation: one move per defect, no search. Anything else — a cell with no depth-3 target at all (mid-block corner cells have none), or a residue that is not a roll about its own slot axis — cannot have come from this generator set and is reported as a structured failure. Final success is gated on `isExactlySolved` over all 8000 cells after replaying the complete move list.

## Invariants

- Cell identity: no cell is created or destroyed; every output move is a legal, physically admissible frame or extension target replayable by the Play reducer.
- Determinism: same input state and solver version produce the same output (inherited from the macro Level 2 solver, which is itself deterministic).
- Phase isolation is structural: the quotient exactness, the legality lift, and the roll-orbit theorem are the three facts each phase rests on, and all three are machine-verified rather than argued.
- Honest failure: torn mid-blocks, internally scrambled blocks, and non-roll orientation residues all produce `success: false` with the failing region or cell named.

## Complexity and measured results

- Phase 1: `O(8000)` cell scan plus `≤ 24` rotation tests per region — `O(400 × 24 × 20)` integer vector comparisons.
- Phase 2: one Level 2 slice-reduction solve over 400 macro cubies (one-time ~2.6 s commutator library build per process, pre-warmable via `warmLevel3BlockQuotientSolver()`).
- Phase 3: `O(moves × 8000)` replay.
- Phase 4: one target lookup and up to three angle trials per twisted cell.

Measured (M-series laptop, 10 seeded scrambles each, the algorithm's declared generator set), after the warm-up build:

| Scramble length | Success | Avg runtime | Avg solution length |
| --- | --- | --- | --- |
| 20 | 100% | ~2.5 s | ~2,307 moves |
| 50 | 100% | ~2.8 s | ~2,597 moves |
| 100 | 100% | ~3.1 s | ~2,723 moves |

Additionally validated by [`research/scratch/l3-validate.ts`](../../research/scratch/l3-validate.ts) — 23/23 scenarios, covering scramble lengths 10–200, roll-heavy scrambles up to 600 moves (which drive ~370 residual twists through phase 4), and honest rejection of scale-1-slice and depth-2.5-slab scrambles. Each scenario re-checks legality move by move and replays independently of the solver's own reporting.

Solution length is inherited almost entirely from the macro solver: the ~2,600 moves are ~2,600 lifted Level 2 commutator moves plus one turn per residual cell roll. Any improvement to the Level 2 slice-reduction word length carries over one-for-one, which is exactly what has happened twice with no change to this file: ~4,300 moves at Level 2 v0.1.0, ~3,000 at v0.2.0 (two cells per 3-cycle), ~2,600 at v0.3.0 (longer pure permutations).

Reproduce from the CLI:

```
npm run bench -- --algorithm=level3-block-quotient --level=3 --count=10 --length=50
```

## Benchmarking and the scramble generator set

The declared `scrambleMovePool` is the block-rigid generator set above, weighted roughly 30% scale-3 / 15% scale-9 / 10% depth-1 / 15% depth-1.5 / 15% depth-2 / 15% cell rolls so scrambles are dominated by block-transporting moves rather than orientation noise.

Unlike the Level 2 pools, this one filters out physically blocked turns when it is built rather than leaving them for the runner to reject: only 744 of 4800 depth-3 targets can turn, so an unfiltered pool would be 80% dead weight.

## Future work

- ~~**Full Level 3 generator set.**~~ — done: the [Level 3 slice-reduction solver](level3-slice-reduction-solver.md) handles the full physically legal generator set and uses this solver as its fast path. Its completion audit removed empirical search cutoffs and records the finite-graph argument and seven legality-checked engine replays. What follows was the analysis before that existed. Scale-1 slices and depth-2.5 slabs need a cell-level reduction — place every cell back into its home mid-block, then apply this quotient. The Level 2 method transfers in principle: hierarchical coordinates `p = 9B + 3b + o` give a 15-class decomposition (by which digits are edge-type and how their zero axes align) in place of Level 2's five, and the class-invariance argument is the same self-similar digit action. The engineering obstacle is tool discovery: Level 2 builds its commutator library by brute force over ~50k move pairs on 400 sites, which does not scale to 17,775 move atoms on 8000 sites. Transporting Level 2's tools through the quotient isomorphism, rather than rediscovering them, is the promising direction.
- **Solution length.** ~4,300 moves is the macro solver's cost, not this solver's; see the Level 2 doc's length notes.
- **Level 4.** The tower argument is level-generic — quotienting level `n` by mid-blocks gives level `n-1` — so this pipeline should recurse. `apps/lab`'s Level 3 rendering is already at its limit at 8000 cells (one mesh per cubie), so level 4's 160,000 cells is a headless/benchmark target only.
